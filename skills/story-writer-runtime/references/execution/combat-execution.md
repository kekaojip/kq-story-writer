# Combat Execution Slice

> Writer 执行切片。只负责把已经批准的战斗、斗法、智斗、装逼/打脸结果写成连续正文，不负责设计胜负、技能、反转、敌人、奖励、升级或爽点。

## 权威输入

战斗必须服从：

1. `04_BOUNDARIES.md`
2. `01_OUTLINE.md`
3. `02_CURRENT_STATE.md`
4. `benchmark/EXECUTION_CARD.md` 的 `COMBAT` 模块（若存在）
5. 人物/规则文件中已发布的能力边界

没有写进上游输入的技能、装备、底牌、代价或结果，不得为了让战斗精彩而自行补造。

## 1. 战斗先写结果逻辑，再写动作表面

Writer 不重新设计战斗，只执行已批准的因果：

- 谁先占优势；
- 哪个已知手段改变局面；
- 哪个动作/判断导致胜负；
- 最终谁赢、谁退、谁受伤；
- 哪个爽点或压迫感必须被读者看见。

正文动作必须服务这些批准结果。没有结果功能的连续拳脚、法术名称或姿势清单应压缩。

## 2. 首次展示与重复展示

- 新能力/大招首次正式展示且上游要求突出时，可以展开其可见效果、代价与环境反馈。
- 已经在前文充分展示过的招式，后续优先写结果、差异和对手反应，不重复同一套说明书。
- 技能喊名可按题材习惯保留，但不等于每次都要解释原理。

## 3. 节奏

战斗不匀速。

可以出现：

`试探 → 压力上升 → 空隙/判断 → 爆发 → 结果`

也可以直接秒杀，只要这就是批准结果。

不要为了“更精彩”强行加入假败、第二阶段、临时底牌或额外敌人。

## 4. 视角与信息

- 只写当前 POV 能理解到的战斗信息。
- 角色不知道机制时，可以写现象、压力和推测，不替角色补全规则答案。
- 智斗依赖信息差时，严格服从上游已经批准的双方知识边界。

## 5. 爽点呈现

爽点已经由主模型决定，Writer 只负责让它可见。

可用：

- 结果反差；
- 对手此前建立的强度与当前失败形成的落差；
- 已批准的旁观者差异化反应；
- 资源/身份/能力产生的具体现实后果；
- 主角选择本身体现出的从容、狠决、判断或控制力。

禁止为了放大爽感新增围观者、身份揭露、额外奖励或未批准羞辱桥段。

## 6. 动作写法

- 动作词优先于形容词堆叠。
- 连续动作必须有因果，不写监控录像式“拿起、转身、抬手、迈步”清单。
- 伤势与身体反馈只有影响动作、判断或结果时展开。
- 高魔/规则型战斗重在“什么规则造成什么结果”，但只解释当前必要部分。

## 7. 与 Human Writing L2 的关系

- 不把每次攻防都解释完整。
- 已经由结果说明强弱时，不再补“可见其多么强大”的总结。
- 允许某些招式一笔带过，某些关键动作放大，不要求平均展开。
- 不为制造真人感随机插入口头梗、停顿或碎句。

## 8. 自检

- 胜负有没有被改？
- 是否出现未批准技能/底牌/敌人/奖励？
- 是否为了爽新增了剧情？
- 是否把战斗写成动作清单？
- 重复招式有没有重复解释？
- 关键结果是否真正落到了场景里？
